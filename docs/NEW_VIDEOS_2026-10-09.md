## Есть ли проблема с детекцией и центрированием

Сообщение «больше половины записи» относилось к ходу ещё работавшего сканирования. Теперь все четыре прохода завершены. При этом ограничение частоты действительно влияет на результат:

- **N1-003 → N1-004**, первая запись: первые данные показывают только край машины, затем полный кузов. На кадрах 4925–5050 проверен каждый кадр, всего 126. С шагом в секунду получаются два трека, покадрово — один. Единственный кадр в допуске линии — **5021** (смещение центра 1,92 px); ближайший секундный кадр 5025 имеет смещение 67,25 px.
- **N2-014 → N2-015**, вторая запись: на кадрах 12550–12675 аналогично 126 покадровых проверок дают один трек вместо двух. Кадр в допуске — **12651** (7,12 px); секундная выборка берёт 12650 со смещением 26,35 px.

В этих двух эпизодах машины обнаруживаются. Разрыв создаёт редкое связывание рамок; строгий допуск ±10 px на линию секундный проход пропускает. Оба проезда остаются в общей проверке. Из двух эпизодов нельзя вывести полноту обнаружения остальных машин или измерить задержку рабочей камеры.

Проверен настоящий `find_video_crossing` с повторным запуском YOLO на соседних исправленных кадрах. Он нашёл кадр 5021 после 11 проверок и кадр 12651 после двух. Оба восстановленных кадра успешно сохранены станцией с длинами 4,578 и 4,961 м. Эти две дополнительные записи относятся к тем же проездам и **не добавляются** к числу 168. Механизм восстановления уже был в приложении; этот прогон проверяет его на новых данных, а не объявляет его новым исправлением.

Практический вывод: центрирование нельзя использовать как единственное условие сохранения автомобиля. Нужны наблюдения до/после линии, поиск по буферу реальных кадров и сохранение ближайшего полного кадра для проверки, когда надёжной длины нет. В текущем приложении эти пути предусмотрены; проверка выше не воспроизводит всю работу живой IP-камеры под нагрузкой.

## Воспроизведение

[Все 168 наблюдений](new-videos-selection-2026-10-09.json), [16 кадров для каталога](new-videos-catalogue-selection-2026-10-09.json) и [полный компактный результат](new-videos-audit-2026-10-09.json) содержат контрольные суммы входов, моделей, кода и фото. SHA256 новых видео не пересекаются с прежними шестью записями; камера та же, физические машины могут повторяться между датами.

```bash
.venv/bin/python scripts/audit_additional_captures.py \
  --selection docs/new-videos-selection-2026-10-09.json \
  --profile config/st-wheel-recovery-calibration.json \
  --weights runs/accuracy_10cm/models/yolo26m.pt \
  --video-dir /home/user/Downloads \
  --output-dir runs/new_videos_reproduced --device cpu

.venv/bin/python scripts/audit_sparse_fragments.py \
  --selection docs/new-videos-selection-2026-10-09.json \
  --profile config/st-wheel-recovery-calibration.json \
  --weights runs/accuracy_10cm/models/yolo26m.pt \
  --output-dir runs/new_videos_dense_reproduced \
  --pairs N1-003:N1-004 N2-014:N2-015
```

Для нового сканирования служит `scripts/select_video_audit.py --videos ... --profile ... --weights ... --output-dir ...`. По умолчанию шаг 1 с. После завершения `--reuse-scout --all-tracks` записывает все треки в `all-selection.json`; исходные хеши и фото проверяются. Этот инструмент не оценивает recall детектора.

Локальная галерея всех 168 наблюдений: `runs/new_videos_20261009/index.html`. Фото 2592×1944 в `replay-N1`…`replay-N4` побайтово сверены с полными фото станции и кадрами сканера. Маски, полные записи, SQLite, исходные журналы детекций, покадровая проверка и восстановленные кадры остались в этой локальной папке. Галерея показывает только полные исправленные снимки. Производственная база и калибровка не изменялись; CPU разрешался только в изолированных офлайн-процессах.
